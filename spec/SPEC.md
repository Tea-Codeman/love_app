## 1. Objective（目标）

**做什么**：一个微信小程序，以"关系成长"为核心驱动力，用「轻社交社区 + 双人轻互动小游戏」让单身用户从陌生 → 好感累积 → 信任，关系自然发生，最终**促成真实伴侣关系**。

**为谁**：
- 核心用户：20–28 岁、一二线城市的单身年轻人。
- 痛点：嫌探探"太看脸、太直接、像相亲"，Soul"太飘、难破冰、容易聊死"。
- 他们想要：先有共同话题与轻松互动、关系自然发生；并对"看到一段关系在成长/有进度"本身有情绪价值。

**为什么是微信形态（关键优势）**：
- 微信内即用，免下载独立 App。
- 微信内闭环加好友（展示二维码长按识别 / 复制微信号），免跳转下载其他 App，把体验摩擦降到独立 App 没有的低点——这是相对现有产品的硬护城河。
- ⚠️ 修正：微信小程序**没有**"一键加微信好友"的官方开放 API（官方指引为长按二维码识别），故 F6 走"解锁联系方式 + 引导添加"的微信内闭环，而非零摩擦直达通讯录。

**v1 成功定义（北极星）**：**真的有人通过它交到伴侣，并成为留存用户**。具体可量化信号 = "关系成长是否真发生"（见 §8 Success Criteria）。

**v1 不做**：情侣深度经营、任何营收/内购、重度竞技游戏、(B) 共同任务挑战的复杂化、你画我猜类高实时游戏。v1 只打「社区融入 → 游戏结识 → 自然升温 →（导向）恋爱」单身主链路。

## 2. ASSUMPTIONS（已决议，核对无误）

1. 形态为**微信小程序**（非独立 App、非 H5），用 **uni-app（Vue3 + Vite）** 构建并编译到 mp-weixin（前端框架已在 Plan 阶段由用户签字定为 uni-app）；现有 workspace 原生骨架将在 M0 迁移为 uni-app 结构。
2. **后端与实时通信（T5 + T1 已决）**：后端 = **微信云开发 CloudBase**（云函数 + 云数据库 + 云调用）；实时双人互动 = **弱实时**——首款游戏为回合制默契问答/选择题配对，用云数据库 watch 或轻量 WebSocket 即可（秒级足够），无需原生 WS 集群。
3. 账号体系以**微信 openid** 为唯一身份，不强制手机号注册（压低门槛）。
4. **"关系成长值"= 两人之间的好感度/信任度**（非个人等级）；靠反复轻游戏互动累积；**P1 已决**：5 阶段 S0–S4，值**只增不减**（阈值随版本校准，见 §6）。
5. 数据合规遵循《个人信息保护法》与微信平台规范；**T3 已决**：内容安全用微信免费 API（msgSecCheck / mediaCheckAsync），UGC 必须接入方可过审。
6. v1 **不接入支付/内购**（变现后置），但数据结构预留虚拟道具字段位。

## 6. Code Style（示意，待 Plan 固化）

小程序以 JS 为主，约定（草案）：
- 命名：页面/组件目录 `kebab-case`，函数 `camelCase`，常量 `UPPER_SNAKE`。
- 状态/数据：页面用 `data`，跨页面用 `globalData` 或云数据库。
- 提交/校验：所有用户输入经 `utils/validate` 校验，外发内容经 `utils/security`（F8）过滤。

**关系成长模型（P1 已决）**：
- 两人共享**一条**关系成长值（模拟"关系"而非个人），值**只增不减**。
- 5 阶段（S0→S4）：
  - **S0 陌生**：刚匹配/刚进游戏，成长值 0
  - **S1 有点意思**：完成首场游戏 + 互回 → 解锁轻聊
  - **S2 聊得来的朋友**：≥3 场互动 + 互加游戏好友
  - **S3 有好感**：持续多日正向互动
  - **S4 信任·可加微信**：成长值达阈值 → 解锁联系方式，引导至微信添加
- 累积规则（草案）：每次一起玩 +X、每次高质量互回 +Y、连续天数加成、双向正向反馈翻倍；具体阈值在 Plan/实测中校准。冷关系靠"最近互动"排序自然沉淀，**不衰减**。

示例（关系成长值累加，示意）：
```js
// utils/growth.js —— 两人关系成长值累加（示意，非实现）
function addGrowthPair(pairId, delta) {
  if (delta <= 0) return;                 // 只增不减，好感靠累积
  return db.collection('pairs').doc(pairId).update({
    data: { growth: db.command.inc(delta), updatedAt: Date.now() }
  });
}
```

## 8. Success Criteria（成功标准，可测）

v1 "成功" = **关系成长真发生 + 有人交到伴侣 + 留存**。建议量化门槛（初版，待 F9 校准）：

- **SC1 关系成长真发生**：配对用户中，走到「聊得来的朋友（S2）」及以上阶段的比例 ≥ **30%**（P1 阶段划分确定后修正）。
- **SC2 留存**：配对后 **7 日留存 ≥ 25%**（dating 品类基准参考，待实测校准）。
- **SC3 导流现实关系**：配对用户中最终**解锁联系方式并加微信**的比例 ≥ **15%**（注：微信无"一键加好友"官方 API，走二维码/微信号闭环）。
- **SC4 终极验证（北极星）**：上线窗口期内，**有可归因的真实伴侣关系形成**（问卷/回访 + 加微信后关系主页里程碑达成），作为定性+定量证据。
- **SC5 安全底线**：内容违规在 F8 机制下 **24h 内处置率 ≥ 95%**，无重大合规事故（T3）。

> 门槛数值为初版假设，需用 F9 早期数据回灌校准；SC4 是产品存在的根本理由。

## 9. Boundaries（边界）

**Always（始终遵守）**
- 任何 UGC / 私聊外发内容经 F8 合规校验后发出（微信内容安全 API）。
- 所有用户输入在服务端校验，不信任前端。
- 关系成长值只增不减（好感靠累积，模型见 §6）。
- 改动前先更新本 Spec，再写代码（Spec 是活文档）。

**Ask first（先问再做）**
- 前端框架变更（**已决 = uni-app**，不再变更，除非重新评审）。
- 引入第三方依赖 / SDK（尤其 IM、风控、地图）。
- 触碰数据模型 / 隐私字段（T3 合规）。
- 任何涉及营收/内购的改动（v1 明确不做，后置）。

**Never（绝不）**
- 提交密钥 / openid 映射 / 用户隐私明文到仓库或前端。
- 在 v1 加入情侣经营或变现功能（已确认 Out of scope）。
- 跳过内容安全审核直接上线 UGC。
- 用假数据伪造"关系成长/交到伴侣"指标。
- 使用非官方"个人微信协议"类接口实现加好友（违规、有封号风险）。

## 10. 决策记录（Open Questions 已全部决议）

**技术侧**
- **T1 实时互动方案【已决】**：弱实时。v1 首款游戏为回合制（默契问答/选择题配对），用云数据库 watch 或轻量 WebSocket（秒级）即可，不建原生 WS 集群。

- **T5 技术栈/架构【已决】**：微信云开发 CloudBase（云函数 + 云数据库 + 云调用），免运维、与小程序原生集成。

**产品侧**
- **P1 关系成长建模【已决】**：5 阶段（S0 陌生 → S1 有点意思 → S2 聊得来的朋友 → S3 有好感 → S4 信任·可加微信）；双人共享一条成长值，**只增不减**，靠"最近互动"排序沉淀冷关系（详见 §6）。
